# BUN Binary Asset Parser

A C11 command-line tool that parses and validates `.bun` binary asset bundle files, and its 39 libcheck tests all pass (`make test`, last run 23 Oct 2026: `100%: Checks: 39, Failures: 0, Errors: 0`).

Every offset, size and count in a `.bun` file comes from the file itself, so the parser treats all of them as hostile, checks bounds before it seeks or allocates, and reports every violation it finds rather than stopping at the first one.

Built in a four-person university team in 2026. The specification and the provided sample files aren't included, so the test fixtures here are generated by my own `bunfile_generator.py`.

## How to run

Needs `gcc`, GNU `make`, `check`, `pkg-config` and `python3`. On Ubuntu or WSL:

```sh
sudo apt install build-essential check pkg-config python3
make                                   # builds ./bun_parser
python3 bunfile_generator.py --all     # writes 29 sample files (6 valid, 23 invalid) to tests/fixtures/
./bun_parser tests/fixtures/valid/01-empty.bun
```

Exit codes:

| Code | Symbol              | Meaning                                      |
|------|---------------------|----------------------------------------------|
| 0    | `BUN_OK`            | File is fully valid                          |
| 1    | `BUN_MALFORMED`     | File breaks the format rules                 |
| 2    | `BUN_UNSUPPORTED`   | File uses a feature the parser doesn't do    |
| 3    | `BUN_ERR_IO`        | Generic I/O error                            |
| 4    | `BUN_ERR_NOT_FOUND` | Path doesn't exist                           |

## What broke

- **The overlap check could wrap.** The first `sections_overlap()` computed `offset + size`, and because the past-EOF checks record a violation and keep going (so every problem gets reported), out-of-range 64-bit values from a hostile file could still reach it and wrap past zero, which reads as "no overlap". Code review caught it, and it now compares the gap between the two offsets against the size of the lower section, so there's no addition left to overflow.
- **A record count can ask for 206 GB.** A file can declare `asset_count = UINT32_MAX`, about 4.3 billion 48-byte records, so any count over `BUN_MAX_RECORDS` (1,000,000, which is 48 MB) is refused with `BUN_UNSUPPORTED` before `calloc` runs, and the asset table is bounds-checked against the file size first. A merge had left a second, unreachable copy of that cap with a comment saying 56 MB (it's 48), and the same review cleaned both up.

## Status and limits

- Finished coursework, not maintained.
- zlib-compressed assets return `BUN_UNSUPPORTED`, and non-zero checksums are reported, not verified.
- Linux/WSL only (it uses `fmemopen` and POSIX `fseeko`).
